# Hodgepodge 项目开发准则

版本：v1.0；更新：2026-10-13；适用：项目自有代码、蓝图、配置、工具、测试，以及具体实现方案的讨论和评审。

## 1. 目标与规则入口

减少重复建设、初始化和网络时序错误，保证新增功能可以配置、验证和维护。新代码必须有中文注释；提出具体方案前必须核查 Lyra，已有成熟详细实现直接复用。

- [AGENTS.md](../../AGENTS.md)：任务启动必读，保存全项目关键约束。
- [AI 开发与验证流程](../AI_DEVELOPMENT.md)：本机构建、编辑器操作与验证步骤。
- 本文：中文注释、Lyra 复用流程和补充工程约定的完整定义。
- `.cursor/rules`：向工具提供简短入口，具体细则引用上述文档，避免分别维护不同版本。

当前用户对任务的明确要求优先。更改准则时同步相关入口；历史设计和历史测试记录不自动证明当前功能状态。

## 2. 中文注释：强制要求

所有新编写或实质重写的项目自有代码必须包含中文注释，覆盖 C++ 头文件／实现、C# 构建规则、Python 脚本、测试以及蓝图关键逻辑。蓝图使用注释节点或适合的说明字段，不创建无意义节点来凑注释。

注释简洁明了，尽量一行说明一个功能点。应覆盖文件或模块用途、类职责、函数契约、含义不直观的参数与返回值、关键状态、权限与生命周期处理。简单变量不重复翻译名称；重点说明为什么这样处理以及适用条件。

- 文件／类头可用中文 Doxygen；必要参数、单位、成功或失败语义用 `@param`／`@return` 说明。
- 函数体内连续 `//` 注释块最多 3 行，禁止通过插入空行绕过限制；较长设计依据放文档并引用。
- include 不需要注释；注释应贴近对应代码，改变逻辑时同步更新。
- 保留 Epic 和其他第三方版权、许可及来源说明；不将英文许可替换为中文，不修改 UE 生成文件。
- 不为补注释改变行为、结构或声明顺序；不顺手重命名已有资产、类型和拼写。

示例：

```cpp
/** 释放本次动作的方向占用；执行身份不匹配时保留新动作资源。 */
void ReleaseFacingForExecution(FGuid ExecutionId);

// 旧动作的迟到回调不能清理当前动作。
if (ExecutionId != ActiveExecutionId)
{
    return;
}
```

上例仅说明注释风格，不代表项目新增了该接口。审查依据是说明是否准确、必要且能帮助维护，不以注释行数或比例验收。

## 3. 设计前核查 Lyra：强制要求

本机参考根目录：`E:/Project/UProject/study/Epic/LyraStarterGame`。其 `.uproject` 当前声明 EngineAssociation 为 5.5；本项目保持 UE 5.5.4，不因为复用自动升级引擎或插件。

每次讨论或设计具体实现前执行以下流程：

1. 明确功能、输入／输出、权限、生命周期和验收目标，识别本项目现有入口。
2. 用 `rg --files`／`rg` 检索 Lyra 的 Source、Config、Plugins；需要资产信息时检查对应蓝图或 DataAsset，不能用文件存在代替内部配置核查。
3. 阅读相关实现及调用者，追踪创建、初始化、授予、正常执行、取消、解绑和销毁。确认 Build.cs、GameFeature、GameplayTag、复制和资源加载依赖。
4. 判断实现是否完整且适用；找到同名类、空函数、TODO 或 `unimplemented()` 不等于找到成熟详细实现。
5. **已有成熟详细实现时直接复用其实现方案和必要代码链路**，沿用项目 Hodge 命名、模块和已有服务做最小适配。已经迁入的功能继续复用当前实现，只修缺口。
6. 无对应实现、仅部分实现或与约束确实冲突时，列明检索文件和原因，优先使用引擎已有能力，再设计必要的项目扩展；不凭印象认定 Lyra 没有实现。
7. 写明参考文件／函数、保留的机制、适配差异、资产与依赖、剩余缺口及测试范围，然后进入编码。

复用包含职责、调用关系、数据结构、资源归属与清理，不只是复制某个算法或函数。不得为了照搬 Lyra 引入本项目明确不使用的 CommonGame／CommonUser，也不为普通怪物强行增加 PlayerState。适配改变了生命周期、复制或错误处理时，解释差异并验证对应场景。

参考路径不可用时，先核对位置或寻找同一本地参考项目，必要时请求路径；明确标记未核实，继续不依赖该结论的只读排查。不能将访问失败解释为 Lyra 没有该功能。

### 3.1 常用检索入口

以下路径均相对于 Lyra 根目录，仅作为查阅起点，不能跳过具体任务的调用链核实：

- 初始化和 Pawn 切换：`Source/LyraGame/Character/LyraPawnExtensionComponent.cpp`、`LyraHeroComponent.cpp`。
- Experience 与玩家机器人：`Source/LyraGame/GameModes/LyraExperienceManagerComponent.cpp`、`LyraBotCreationComponent.cpp`。
- 玩家 ASC 与能力授予：`Source/LyraGame/Player/LyraPlayerState.cpp`、`Source/LyraGame/AbilitySystem/LyraAbilitySet.cpp`、`LyraAbilitySystemComponent.cpp`。
- 扩展授予：`Source/LyraGame/GameFeatures/GameFeatureAction_AddAbilities.cpp`。
- 库存／装备／快捷栏：`Source/LyraGame/Inventory/LyraInventoryManagerComponent.cpp`、`Source/LyraGame/Equipment/LyraEquipmentManagerComponent.cpp`、`LyraQuickBarComponent.cpp`。
- 相机：`Source/LyraGame/Camera/LyraCameraComponent.cpp`、`LyraCameraMode.cpp`；CameraModeStack 类型位于后者，不假定存在同名独立文件。

本轮已核实的例子：PawnExtension 通过 Init State 协调和注册后立即查询机制推进依赖；AbilitySet 保存授予句柄并由权限检查后的撤销路径清理；CameraComponent 通过模式栈求值应用最终视图。这些是应优先复用的机制，不能直接视为 Hodgepodge 同名流程已完整实现。

同一本机 Lyra 的 `FLyraInventoryList::AddEntry(ULyraInventoryItemInstance*)` 仍调用 `unimplemented()`，`CanAddItemDefinition()` 仍有容量／唯一性 TODO。后续库存开发须复用已完成部分并补齐所需缺口，不能原样迁入后声称完整库存功能可用。

## 4. 架构与职责：补充约定

- 优先沿用 Experience、PawnData、GameFeature、GAS、Init State、现有 Combat 与 CameraMode 链路；不另造重复入口或平行状态机。
- 同一状态明确事实来源、唯一修改入口和最终执行者。角色方向、根运动、相机和动画允许多方提交请求，但由现有仲裁链路统一应用，避免多个 Tick 同时直接写 Rotation。
- Init State 表达初始化生命周期；死亡、受击、暂停等运行约束由现有动态状态或 GameplayTag 表达，不用倒退初始化状态实现行动限制。
- 保持一个 Hodgepodge 业务 Runtime 模块和 Public／Private 对应目录；保留已有 Editor 工具模块，Runtime 不无条件依赖 Editor。
- 同一项目自有 C++ 类的非内联实现集中在主 `.cpp`，不拆功能片段或 include 其他 `.cpp`。独立类、测试和生成代码按已有约定处理。
- 公共接口说明调用条件、权限、成功／失败、单位和资源归属；返回“成功”必须对应实际可验证结果。

## 5. 权限、生命周期与错误处理：补充约定

- 玩家 ASC 的 PlayerState Owner 与 Pawn Avatar、普通怪物 Pawn 自有 ASC 分别核实，不能用同一所有权假设覆盖两类角色。
- 能力授予、伤害与关键状态由服务器权威决定；拥有者预测与模拟代理表现职责分开。使用 GAS TargetData 仍需验证 Avatar、Spec、PredictionKey、数据合法性与迟到请求。
- 玩家输入与 AI 决策共用现有战斗请求入口，保留各自输入条件和服务器权限，不让 AI 伪造本地玩家输入去绕过约束。
- 初始化可重复调用但不得重复授予、重复装备或重置已消耗生命；先校验依赖，再按步骤确认成功。
- 委托、Timer、技能／装备句柄、动作占用和目标缓存配对释放；基础、装备、GameFeature 各自维护自己的授予句柄。
- 异步回调验证弱对象引用和本次 Pawn／Possess／执行身份；解绑、死亡、换 Pawn、取消和销毁后，旧回调不得恢复旧状态或清理新资源。
- 区分依赖未到达、永久配置错误与运行失败；使用事件重试或必要的有界等待，不无限轮询、不静默跳过必需资源后返回 Ready。
- 日志包含可定位的资产／Actor／请求及失败阶段；不输出凭据、访问令牌或无关隐私数据。

## 6. 配置、资产和临时实现：补充约定

- 手感、时间、角度、阈值及资源引用优先放现有配置资产，说明单位、默认值和校验范围；稳定协议常量不必为了可调而资产化。
- 临时实现记录文件、模块、原因、影响范围、退出条件及后续优先级；占位页面不能计为业务功能完成。
- 修改类名、反射字段、GameplayTag 和资产路径前核对蓝图、配置和重定向；保留既有 `Dafult`／`PlayState` 拼写。
- 资产制作先核对实际引用和原配置，保存明确的目标资产；不批量重存无关蓝图、骨架或材质，不覆盖用户调整。
- 软引用声明清楚加载契约；资源未驻留和配置缺失分别处理。自动配置工具支持重复运行，失败时不给出虚假成功结果。
- 新增 Tick、每帧骨骼采样、查询或同步加载前说明必要性；优先已有事件／任务，按受影响场景验证开销，不用降低正确性换取未经测量的性能结论。

## 7. 测试、文档与提交：补充约定

按 [AI 开发与验证流程](../AI_DEVELOPMENT.md) 执行常规 Editor 构建；Runtime 或依赖变化再执行 Game 构建。反射布局、继承和默认子对象变化后关闭已保存编辑器构建，再冷启动核对受影响蓝图。

测试围绕需求和风险，覆盖正常流程、非法配置、重复初始化、取消／清理以及本次修改影响的网络或生命周期边界。修复实际问题时保留有价值的回归用例，不用镜像实现的低价值测试凑数量。

验收分别标注 C++、蓝图、单人 PIE、Listen Server、PIE Dedicated、独立进程、Cook／打包的实际状态。PIE Dedicated 不等于独立专服，网关或脚本启动成功不等于玩法断言通过；故障注入与真实 RPC 测试明确区分。

交付列出改动、Lyra 对应关系、实际命令和结果、问题与未验证项；配置步骤给出真实资产路径和已存在字段。需要覆盖率时提供实际工具结果，或明确只有需求／用例覆盖，不虚构百分比。

文档同步最终接口、资产配置和实施状态；历史记录保留日期和范围。默认不自动提交或推送，用户明确授权后按职责和依赖分批，生成目录、缓存、凭据及日志不入库。需要入库的二进制资产检查 Git LFS。

## 8. 最小方案与交付检查清单

具体方案应包含：需求与范围、Lyra 核查依据及复用内容、本项目实际调用链、接口和数据、权限与生命周期、异常及资源清理、配置／资产、验收用例和暂缓项。

提交交付前确认：

- [ ] 新代码有准确、简洁的中文注释，未修改无关结构或第三方许可。
- [ ] 设计前已核查 Lyra，成熟实现已复用，适配差异和未完成部分明确。
- [ ] 状态控制权、初始化幂等、授予归属和旧回调失效正确。
- [ ] 可调配置与真实资产接线完整，配置错误可定位。
- [ ] 受影响的构建、蓝图及玩法测试已执行，未执行项如实说明。
- [ ] 文档与当前实现一致，用户已有工作完整保留，提交／推送有明确授权。

本文是开发规则更新，不表示所有现存代码已重新审查，也不启动库存或其他后续功能的实施。
