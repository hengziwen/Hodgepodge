## 2. 核心实现逻辑分析

### 2.1 实际调用链与职责归属

当前近战主链并非由 OnDamageAccepted 单独驱动整个受击系统，其主要顺序是：

1. Combat 接收动作意图，选择转换边并通过 ASC 进入 Definition 执行。
2. Definition 维护本次 ExecutionId、动画、朝向数据及通知资源。
3. 动画通知建立检测窗口；检测任务与组件生成带执行身份的命中批次。
4. Melee 校验服务器权限、批次身份、来源和目标，再通过防御入口检查命中是否允许。
5. SubmitMeleeHitEffects 先调用目标 BeginHit 建立本次受击结算身份，再提交伤害 GE。
6. HealthSet 消费 Damage Meta、夹取生命，并记录本次实际接受结果；需要角色结算规则时，Melee 的临时观察者只累计同一结算身份的伤害。
7. GE 同步处理结束后，Melee 调用 FinishHit，由目标按接受结果、Body、分段击飞资格或削韧进度裁决受击。
8. BuildPlan 计算计划，SubmitPlan 执行控制与中断；受击 GA 播放主动画并提交 CMC／RootMotionSource 运动，状态复制与本地表现沿现有链路分工。

关键源码：[Melee](../../Source/Hodgepodge/Private/AbilitySystem/Abilities/HodgeGameplayAbility_Melee.cpp)，SubmitMeleeHitEffects，473～546 行。

这条链保留了伤害与反应的不同职责：实际伤害、强控制资格、动画播放和位移执行彼此关联，但不是一个布尔结果。后续迁移必须保留这种区别，尤其不能把一次表现失败等同于没有扣血，或由动画是否播放反推真实命中。

### 2.2 命中几何：F01 的契约修复

原问题是 ExistingSource 的 Socket 捕获未把来源球半径写入捕获几何，Overlap 路径因而可能使用不完整几何；这与通知窗口是否开启是不同层面的问题。

当前 [HodgeHitDetection.cpp](../../Source/Hodgepodge/Private/Combat/HodgeHitDetection.cpp) 中 UHodgeSocketSweepStrategy::Capture 在 263 行明确保留 Source.Radius。来源、采样点和查询几何继续由现有检测链处理，没有重新建设检测服务。

评估：

- 正确性：修复半径传递，使声明的检测范围进入实际查询。
- 一致性：Overlap 与 Sweep 使用同一来源半径语义。
- 范围：已存在真实检测会话的内外边界回归；完整装备切换、销毁与重绑生命周期不能由几何测试替代。
- 性能：没有同负载数据证明该修复带来整体性能收益。

### 2.3 伤害事务：F02 的同步重入与事件快照

关键源码：[HodgeHealthSet.cpp](../../Source/Hodgepodge/Private/AbilitySystem/AttributeSet/HodgeHealthSet.cpp)，PreGameplayEffectExecute、PostGameplayEffectExecute，135 行、199 行起。

当前处理的关键顺序为：

1. 保存本笔 GE 执行前的生命和最大生命快照。
2. 读取待消费 Damage，并在可能触发同步回调前清零 Meta Attribute。
3. 计算、夹取并设置本笔扣血结果。
4. 用本笔前后生命计算 Accepted，而非重新读取其他嵌套事务的变化。
5. 广播本笔 OnDamageAccepted 和 OnHealthChanged 快照；死亡依据实时生命并去重登记。

以用户确认的同步追加伤害为例：外层 100→90，在其回调中立即追加内层 90→85。最终只扣 15，外层不会因内层执行重复消费原有 10 点 Damage。两笔通知保持各自历史结果；内层可以先完成，订阅者不能假定事件快照按当前生命单调排列。

因此，HUD 应查询当前真实生命，不能把较晚收到的外层历史快照直接覆盖为实时生命。死亡广播前先登记耗尽状态，可以避免死亡监听器重入导致重复通知；有生命恢复时仍需重新允许下一次合法耗尽。

Accepted 继续表示实际生命损失。剩余 10 血、结算伤害 100 时，接受伤害为 10；本轮没有改变伤害公式或引入另一种显示数值语义。

该实现解决已确认的伤害重入问题，不代表所有属性、恢复、复活和换 Pawn 组合已经完成网络验收。

### 2.4 连段判定：F03 与服务器有界等待

关键源码：[HodgeCombatComponentBase.cpp](../../Source/Hodgepodge/Private/Component/HodgeCombatComponentBase.cpp)，EvaluateTransition，219 行起；[HodgeAbilitySystemComponent.cpp](../../Source/Hodgepodge/Private/AbilitySystem/HodgeAbilitySystemComponent.cpp)，ProcessDeferredComboRequest，959 行起。

本地选边和服务器等待共用 Ready／Wait／Reject 判定，保留窗口、来源标签、目标能力和转换优先级。

必须区分两个已确认场景：

- 同一目标动作同时有开放边与闭窗边：合法开放边不能被同目标闭窗边错误阻塞。
- 普通下一刀已经开放，但客户端请求的是另一条派生攻击：继续短暂等待所请求的派生窗口，不擅自改成普通下一刀或立即拒绝。

服务器仍通过现有队列和 Timer 有界等待。来源动作取消、身份失效、超时后，应按现有激活与失败流程终结，不能由迟到请求恢复旧动作。

新增 DeferredServerPipeline 测试确实推进 World::Tick 并经过生产队列和 Timer，覆盖开窗、超时、来源取消与重复请求；其请求通过测试入口注入，不能等同于客户端预测、实际 RPC 和服务器到达顺序的完整验证。

### 2.5 方向 TargetData：RV01 的持有生命周期

关键源码：[Definition](../../Source/Hodgepodge/Private/AbilitySystem/Abilities/HodgeGameplayAbility_Definition.cpp)，OnAttackFacingData，352～373 行。

UE 5.5.4 的缓存补发会按引用广播缓存 TargetData，而 ConsumeClientReplicatedTargetData 会清空缓存 Handle。原实现先消费后读取，在“数据先到、能力后进入回调”的场景中可能清空正在读取的数据。

当前先复制本次 Handle，再消费缓存；后续数量、类型和朝向应用读取稳定副本。Handle 的本地副本保持数据条目的引用生命周期，不表示深拷贝一套新的网络数据。Avatar、Spec、PredictionKey、ExecutionId、重复处理与迟到数据约束继续保留。

本机 Lyra 的 LyraGameplayAbility_RangedWeapon::OnTargetDataReadyCallback 在 487 行先取得本地 Handle 所有权，549 行再消费缓存。Hodge 复用该生命周期原则，适配已有单条朝向数据，没有引入 Lyra 武器或弹道链路。

参考文件为 E:/Project/UProject/study/Epic/LyraStarterGame/Source/LyraGame/Weapons/LyraGameplayAbility_RangedWeapon.cpp；引擎依据为 E:/UE/UE_5.5/Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/AbilitySystemComponent_Abilities.cpp 的 3784～3791、3974～3985 行。依赖继续使用现有 GameplayAbilities。

TargetDataDeliveryOrder 测试覆盖缓存补发、即时广播、真实 Montage 实例、重复交付及取消后迟到。测试直接绑定生产回调并配置激活身份，未走完整远端激活入口，因此不能单独证明朝向等待 Timer、网络传输与换 Pawn 全链路可靠。

### 2.6 作者入口：F04 的定向精简

本轮没有删除公共结构中的 Reaction，因为 Definition 默认命中配置仍使用它。

攻击 Notify 的有效来源分别为：

| 设置 | 实际职责 |
| --- | --- |
| bUseDefaultDamage | 选择 GE、倍率和伤害标签来自 Definition 还是通知覆盖 |
| bUseDefaultReaction | 独立选择默认 Reaction 或 ReactionOverride |
| Notify.Damage.Reaction | 在该通知入口不消费，已定向隐藏；历史序列化值继续保留 |
| bCanLaunch | 始终由当前攻击段提供，不能由默认 Reaction 或旧 Impact 重新取得资格 |

这种处理保留四种默认／覆盖组合，降低误配，而不让 UI 整理改变其他入口行为。几何 Validate 同时按实际来源、形状和目标策略缩小检查范围，避免隐藏参数继续无条件阻断合法配置。

作者面测试使用实际属性详情树，但不等于全体正式攻击资产已经逐项迁移或接受过手工编辑验证。当前完整入口和兼容优先级见[第一批整改记录的 F10 登记](../Validation/combat-review-refactor-2026-10-18.md)。

### 2.7 受击裁决：削韧、分段击飞与 Body 的边界

当前削韧进度保留轻／重硬直，不再通过累计达到更高阈值自动转为击飞。击飞与续飞资格来自当前攻击段 bCanLaunch。

这不表示该开关无条件强制播放 Fly：合法命中、目标 Body、移动执行条件、资源完整性、续飞次数和控制链上限仍会参与裁决。

目标已处于受击 Airborne 时，允许续飞的攻击可按现有限制提交新的 Fly；未允许续飞的命中不重启 Fly，沿原弹道、落地、倒地和起身路径恢复。不能为了补反馈重新通过旧 Impacts 或累计削韧取得击飞资格。

F05 使独立 Fly 只检查本次消费的目标运动预设，避免无关削韧阈值错误拒绝合法击飞。它没有将全体 Profile 或所有动画路径都视为有效，也不免除实际资源和安全约束。

### 2.8 Profile 校验：F06、RV02～RV04 的分层

关键源码：[HodgeHitReactionProfile.cpp](../../Source/Hodgepodge/Private/Data/HodgeHitReactionProfile.cpp)，ResolvePresentation，80 行起；ValidatePlanPresentation，191 行起；Validate，325 行起。

| 层次 | 责任 | 不应承担的责任 |
| --- | --- | --- |
| 完整资产 Validate | 检查所有配置家族、方向、变体、资源、运动契约与安全参数 | 不能把一次完整资产诊断直接当作每次命中必须整体失败的条件 |
| ResolvePresentation | 返回本次选择的值副本，保留实际方向／阈值歧义 | 不修改资产、不长期持有数组元素指针 |
| ValidatePlanPresentation | 检查当前计划及实际采用的未来阶段资源 | 不授权命中、不取消能力、不播放动画或移动胶囊 |

最新修复补齐三处具体边界：

1. **RV02：未来落地回退。** 空中落地倒地且没有独立 Landing 时，检查实际回退 Knockdown 的必需主片；明确允许无动画的旧契约继续有效。
2. **RV03：跨阶段实际选择。** 空中 Knockdown 改用 AirHit 后，主片校验携带实际 AirHit 选择，并独立验证真正落地主片。不能把任意片段指针变化都当作合法续播。
3. **RV04：实际运动阶段。** 普通削韧按实际主片及会执行的 Landing／GetUp 检查运动来源；未使用的落地或起身标记不阻断地面受击，完整 PawnData 资产政策仍保留。

同级旧动作续播在明确分支中处理：保留原 Montage 和起播时间，移除本次不会播放的新变体歧义。控制身份变化不自动等于动画从零帧重播。

已覆盖的原问题可以关闭，但最终选片后的 AnimInstance 依赖检查仍有残余，见第 4.2 节。校验范围收窄也不等于未来阶段配置已全部冻结：TickPlan、RequestGetUp 和受击 GA 仍会读取 Profile，后续拆分必须明确这些读取的归属。

### 2.9 动作结束：F07 的原类内收敛

关键源码：[Definition](../../Source/Hodgepodge/Private/AbilitySystem/Abilities/HodgeGameplayAbility_Definition.cpp)，ReleaseExecutionResources，563 行起；EndAbility，630 行起。

EndAbility 保持唯一结束入口。原有资源释放块提取到同类私有函数，并在结束保护内执行，保留朝向委托与 Timer、电影会话、执行身份、角色规则、翼、动画委托、武器占用、状态标签和姿势租约的清理归属。

资源释放与 GAS 最终结束没有合并：资源函数不能再次结束 GA、重复发布请求结果，或替代原来的取消复制、动画能力交接、Combat 通知及 Super 生命周期。

Combat 的 SetActionRequestStatus 继续写入本地请求记录并按队列发布通知；RequestId、AbilitySpecHandle、PredictionKey、ExecutionId 与 Avatar 含义不同，不能用一个通用 ID 替代。

这次提取改善了结束入口的可读性，但动作事务仍跨 Combat／ASC／Definition。其收益是原类入口集中，不能计为跨类事务重构全部完成。

### 2.10 验证设计及证据可信度

最新玩家受击脚本按 PlayerState.PlayerId 匹配同一目标，区分服务器、受击拥有者和独立观察客户端。Dedicated 观察断言排除服务器与受击拥有者；双人 Listen 单独报告主机观察，不虚构第三个客户端。

逐端释放快照检查受控、动画根运动、RMS 和已采样受击 Montage 的状态。两项离线失败注入直接提取实际脚本中的纯判定函数，能够验证“服务器冒充观察者”和“已报告残留仍通过”等错误不会被接受。

但判定函数与采集器是不同环节：如果采集器没有报告某个旧动画实例，最终列表为空仍可能通过。因此，离线断言通过不能替代多实例采集完整性检查。

## 3. 优点与亮点

### 3.1 正确性修复针对明确契约

半径传递、Damage Meta 消费顺序、TargetData 持有与真实落地回退均有可解释的失效链。改动集中于明确边界，没有用调整正式伤害、窗口或素材来掩盖失败。

新增风险用例曾在修复前暴露四项失败，修复后通过；这比仅新增与实现同构的断言更有价值。但修复前后测试集后续又有增加，不能把两批数量当作完全相同测试集直接比较。

### 3.2 状态与权限主干得到保留

服务器继续裁决伤害和受击控制，拥有者预测与模拟代理表现保持不同责任。玩家与怪物的 ASC 所有权未被人为统一，分段击飞也没有绕过 Body 或安全限制。

权威受击状态仍由现有组件持有，GA 负责动画及运动执行。没有新增第二份权威状态、第二套命中链或表现 RPC。

### 3.3 作者面精简兼顾序列化兼容

定向隐藏 Notify 中不消费的重复 Reaction，保留 Definition 的有效入口和历史数据。按类型与路径校验减少无关参数误伤，同时没有通过直接删除属性制造简化成果。

### 3.4 可维护性改善具有明确范围

共享选边判定降低规则漂移，Profile 的选择副本与分层校验减少跨方向配置错误扩散，Definition 私有清理入口使结束流程更易阅读。

这些改进应继续保留；它们并未解决所有协调层复杂度，后续仍需在已确认边界内逐步迁移。

### 3.5 失败记录与验证分层较完整

文档保留测试警告数、服务器注入与实际 RPC 的区别、同进程 Dedicated 的限制，以及正式五段失败后的未执行阶段。这使团队能够按证据决定后续工作，而不是仅依据编译成功或测试总数判断。

### 3.6 性能判断保持证据边界

当前没有因为代码行数减少、校验范围缩小就宣称帧率提升，也没有未经测量降低采样频率或合并玩法事件。该约束有助于避免性能整理引入行为变化。

## 4. 潜在问题与改进建议

### 4.1 定性与优先级

- **P1：**应优先处理的已确认高影响正确性问题。本次没有确认新增 P1；不意味着所有历史玩法故障已经解决。
- **P2：**条件性运行缺陷、关键验证缺口和高价值结构／兼容债务。
- **P3：**进一步提高测试精度、阅读和维护效率的改进。

以下建议是评审输出，不自动授权恢复暂缓工作。条件性缺陷、测试工具风险、未执行验证和结构债务分别登记，不把它们合并成“系统已经失效”。

### 4.2 P2：最终主片的 AnimInstance 依赖检查过早

**位置：**[受击组件](../../Source/Hodgepodge/Private/Component/HodgeHitReactionComponent.cpp)，508、510～526、593～604、649～669 行；[受击 GA](../../Source/Hodgepodge/Private/AbilitySystem/Abilities/HodgeGameplayAbility_HitReaction.cpp)，76～79、102 行。

成立条件为：

1. 目标自然下落，尚未进入受击 Airborne。
2. Legacy Knockdown 主片为空，且明确允许无动画。
3. 空中替代用 AirHit 主片有效、与目标 Mesh 兼容。
4. 当前目标没有可用 AnimInstance，其他相关配置可用。

当前 508 行按临时 Knockdown 主片判断，因主片为空跳过动画实例检查。521 行再换用非空 AirHit，后续资源及骨架校验不会补动画实例依赖。

BuildPlan 因而可能成功。SubmitPlan 在 649 行先施加受控、655 行取消旧可中断能力，随后激活受击 GA；GA 在 102 行因缺少 AnimInstance 拒绝。已有动作取消不能由失败清理自动恢复，形成“受击失败但已经产生打断副作用”的条件性问题。

**证据性质：**静态控制流确认；修复前备份同样存在检查先于换片的顺序，属于既有残余，并非本轮新回归。未执行真实复现，未证明正式 Compact 资产触发，也未证明其与终结刀漏判有关。

**改进方向：**在最终主片和续播决策完成后、SubmitPlan 副作用之前，检查实际播放依赖。无动画合法分支继续保留，不能退回全 Profile 一刀切拒绝。

**关闭标准：**缺失最终主片依赖时构建明确失败，旧能力、标签和运动保持未被本次无效计划修改；实际有动画、无动画许可和跨阶段合法选择继续通过。

### 4.3 P2：同资源多 Montage 实例的释放验证不完整

**位置：**[运行时脚本](../../Tools/ACTCombat/validate_poise_runtime.py)，350～356 行；[编辑器采集函数](../../Source/HodgeAbilityEditor/Private/HodgeCombatValidationLibrary.cpp)，InspectMontageState，419～430 行。

脚本按资源路径收集后逐项查询；采集函数从 MontageInstances 末尾找到第一个同资源实例即返回。同一 Montage 连续重播可能同时存在旧混出实例和新实例，因此“被查询实例已释放”不足以证明“全部实例已释放”。

离线失败注入验证的是最终快照判定，未覆盖采集器遗漏。当前也没有证据表明本批实际遗留了旧实例，不能据此否定全部 216 项检查或宣称已发生动画泄漏。

**改进方向：**检查所有匹配实例的播放与权重状态；补多实例失败注入，保留有效实例身份，避免资源路径去重吞掉实例差异。

**关闭标准：**旧实例仍播放或保留可见权重时，即使最新实例已经退出，释放检查仍失败；全部实例真正退出后通过。

### 4.4 P2：测试工具可能覆盖测试前的未保存内存状态

**位置：**[运行时脚本](../../Tools/ACTCombat/validate_poise_runtime.py)，220～225 行。

清理时使用 ASSUME_POSITIVE 无条件重载探针包和临时 Montage。这能清理测试产生的内存改动，但在已有编辑会话中，也可能丢弃同包测试前已有的未保存修改。

最新批次使用独占冷启动编辑器，196 份清单内资产的磁盘哈希一致，未发现该批资产损坏。磁盘哈希不能证明未保存内存修改得到保留，因此脚本可复用范围仍需明确。

**改进方向：**沿已有独占会话约束限制入口，或完整保留并恢复测试前状态；不能将“重新从磁盘加载”直接视为“恢复用户原有编辑状态”。

**关闭标准：**不允许脚本无提示丢弃已有脏包内容；测试自己的临时修改能够退出，用户测试前的有效修改保持。

### 4.5 P2／P3：服务器调度覆盖已有提升，端到端与超时精度仍不足

关键测试：[HodgeCombatActionRequestTests.cpp](../../Source/Hodgepodge/Private/Tests/HodgeCombatActionRequestTests.cpp)，DeferredServerPipeline，473～516 行附近；[HodgeAttackWarpTests.cpp](../../Source/Hodgepodge/Private/Tests/HodgeAttackWarpTests.cpp)，TargetDataDeliveryOrder，187 行起。

已通过用例能够支持生产回调、服务器队列和 Timer 的定向结论，但仍缺：

- 客户端预测、实际 RPC、TargetData 与能力激活的组合到达顺序。
- 普通下一刀开放、所请求派生目标闭窗的完整等待时序。
- 解绑或换 Pawn 时，旧 Timer、旧 TargetData 对新执行的隔离。
- 真实玩家恢复输入、受击中死亡、重生与重新绑定的网络矩阵。

其中，完整生命周期属于 P2 覆盖任务；超时断言精度属于 P3 增强：当前主要检查最终队列清空且目标未激活，可进一步确认截止时间前仍等待、到期后才移除，并确认来源在超时前仍有效，排除其他提前拒绝被当作超时通过。

**关闭标准：**按真实入口、身份和网络拓扑逐项记录结果；明确实际 RPC、服务器注入、同进程 PIE 与独立进程的区别，不以最终位置收敛推断全程没有纠正。

### 4.7 拆分草案：架构方向合理，规格尚不足以直接编码

以下均对应[现有草案](combat-refactor-next-boundaries-2026-10-18.md)，是对既有设计的缺项评估，不新增技术方案或解除暂缓。

#### 4.7.1 第 3 节：无副作用计划解析

拟议 FHodgeHitReactionPlanBuilder 不持久化、不 Tick，不持有 ASC／Actor／GA，不执行中断、动画或运动。组件保留提交与状态，GA 保留执行，边界合理。

当前仍缺三个接口契约：

- **输入完整性：**已有来源朝向，但未明确命中来源位置、来源有效性及方向回退快照；当前计算使用 Hit.Origin 和来源有效性，不能在提取时遗漏。
- **失败输出：**Build 失败后 OutPlan、OutAppliedImpacts 和 OutErrors 如何处理尚未定义，不能让部分结果被误用。
- **后续读取：**TickPlan、RequestGetUp 和 GA 的 Profile 动态读取是否保留，以及与已解析计划怎样保持一致，仍需明确。

这些是迁移前必须确认的规格，不应由实现者在编码时自行决定。当前 private BuildPlan 的输出使用习惯也不能自动当成未来独立接口契约。

#### 4.7.2 第 4 节：局部接触表现

草案正确保留唯一 Multicast、绑定／HitId 检查、去重与服务端诊断；新的表现职责不拥有第二份权威状态，也不带走恢复尾段的权威姿势租约。

尚缺宿主创建和注入、注册／解绑、销毁、Avatar 更换时的归属，以及现有 OnLightFeedback 等事件的兼容接线。移走播放函数之前必须列清这些依赖，否则可能引入双播、漏播或旧 Pawn 回调。

#### 4.7.3 第 5.1 节：本地长按与角色规则

现有 HavocRules 为 ServerOnly，而长按在本地 Pawn 上工作。草案准确指出不能直接把长按搬到活动规则 GA，也不能为方便迁移改变 NetExecutionPolicy。

后续需先确定通用输入订阅、本地职责注入、参数读取和解绑归属，保留普攻 Started 不延迟、松开不补发、20ms 检查和已有有界等待。当前没有这些最终接口，不能将概念边界当作可直接实施的规格。

#### 4.7.4 第 5.2～5.3 节：电影会话与初始化

电影会话仍需完整列出 Source Montage、ExecutionId、Timer、相机栈入口及退出顺序；现有按执行身份结束相机的 API 必须保留兼容。

初始化应区分 Init State 已达到、当前 ASC 绑定有效、当前允许行动。三个查询不能合并成笼统 Ready，其实现者、调用顺序和动态失败语义尚待确认。

#### 4.7.5 第 3.5 节：完成门槛尚未满足

草案要求正式五段与 R、原生、玩家拥有者和观察者均通过。正式五段终结刀仍漏判，因此门槛尚未满足。

用户对漏判排查和拆类的暂缓继续有效。未来恢复迁移前，需要确认是先关闭既有故障，还是批准明确保留失败的限定对照范围；本文不替用户作出选择。草案末尾“下一项需要批准”只是将来候选，不是当前编码授权。

### 4.8 兼容、代码质量与性能风险

**兼容维护成本。** Compact／旧 Animations、显式 Impact／普通削韧、旧收益适配与旧运动路径仍在。它们有保护序列化和既有资产的必要性，但缺逐资产引用台账时，会持续增加作者和维护者判断实际生效路径的成本。

改进应沿已有 F10／RV12：记录实际使用者、入口优先级、迁移证据和退出条件，再讨论删除。不能仅以字段数量衡量完成度，也不能通过清空旧字段破坏行为。

**结构复杂度。** BuildPlan 集中适用性、回退、时长、运动、选片、续播及未来阶段验证；动作事务仍跨三个协调类。长函数与紧凑分支增加阅读负担，但核心风险是契约交叉，不是文件行数本身。职责迁移应保持唯一状态来源和副作用所有者。

**风格一致性。** 当前定点改动总体遵循 Hodge 命名、主实现文件、UE 类型和中文注释约定。尚有既有紧凑条件与兼容注释需要结合实际修改解释，避免以批量格式化扩大差异。本轮不开展无关日志、命名或第三方清理。

**性能证据不足。** 来源查询、LOS、曲线求值和轮询属于原 F11 待测范围。运行时校验缩小到实际路径，理论上减少部分无关工作，但没有同负载 CPU、调用次数或帧时间证据，不宜宣称已消除瓶颈。

后续沿既有测量计划观察这些路径，再决定是否需要优化；不提前新增缓存、改变 Tick／Timer、降低骨骼或命中采样密度，也不任意合并真实伤害事件。
